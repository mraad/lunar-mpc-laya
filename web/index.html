What runs here

Browser MPC is a live simulation, not a recording. The physics and the adaptive MPC are a line-for-line port of the Python package (same constants, substeps, landing rules, cost weights, beam width 32, horizon 15 stages). A Node check replays Python-recorded flights and matches every command. The dashed line is the current 3 s plan; the solid trail is the executed path.

Live Laya runs in Python, not in the browser. With the local server, each decision is a real Laya inference on Apple MLX: MPC computes the requested labels, Laya answers the two choice questions, and in shield mode MPC rolls out Laya's proposal and overrides only when it is predicted worse than its own plan. The browser only draws what the server returns.

Two checkpoints. Laya · MPC requests is the original checkpoint: its prompt carries MPC's requested rotation and power, and it follows them. Distilled Laya was retrained on MPC labels with a telemetry-only prompt; it decides by itself, cannot land unshielded, and lands every recorded flight with the shield while keeping about two thirds of its own choices.

Adaptive vs fixed. The controller is told nothing about the fault. With learning on, the thrust estimate moves toward the true value within a few seconds and the plan changes with it. With learning off it keeps planning for the nominal engine; at ×0.4 that lands too fast. Landing needs |vx| ≤ 2 m/s, descent ≤ 3 m/s, |tilt| ≤ 8° inside the pad. Cost weights were hand-picked on ten development seeds; some starts are unrecoverable and the search has no guarantee.

Python-recorded flights with the actual Laya checkpoint: every decision's probabilities, MPC request, Laya proposal, executed command and shield activity, on the held-out seeds 3000–3009. Build them with python3 web/build.py dist/eval/*laya*.json dist/eval/mpc-assisted*.json.
